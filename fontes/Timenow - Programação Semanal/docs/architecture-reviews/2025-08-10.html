1. Boot sequence monolith in index.html

app/index.html — #app-shell x-init

Strong

Problem

The entire boot sequence lives in a single x-init async IIFE on #app-shell. In one anonymous block it:

  • Fetches /.auth/me to check auth state
  • Conditionally loads the login gate or the nav + deep-linked view
  • Contains the routing logic (which view for which path)
  • Handles no obvious error boundaries — any exception in the IIFE leaves the user staring at a spinner forever

The interface (a single x-init attribute) is nearly as complex as the implementation. This is a textbook shallow module: the deletion test — if you delete this block, the complexity doesn't vanish; it's all still needed, just scattered across even more places.

Solution

Extract the boot sequence into a small JavaScript module in app/_shared/boot.js with a clear interface:

  • boot() — orchestrates the flow: auth → gate or nav + route
  • checkAuth() → { user | null } — single auth check, cached
  • loadView(path) — loads a fragment into #app-shell
  • showLoginGate() — loads /login.html

index.html then calls boot() in its x-init. The nav template no longer calls /.auth/me; it reads from the shared cache.

Benefits

  • Leverage — a one-line <main x-init="boot()"> replaces ~40 lines of inline code. Callers (future views) get a cache of auth state.
  • Locality — auth logic, routing, error handling live in one file instead of being split between index.html and nav/main_nav.html.
  • Testability — unit-testable: mock fetch, call checkAuth(), assert it only hits /.auth/me once.
  • Eliminates the duplicate auth call — the nav currently fetches /.auth/me again independently.

2. Duplicated auth check across front-end modules

app/index.html + api/src/templates/nav/main_nav.html

Strong

Problem

The /.auth/me endpoint is called twice on every page load:

  1. In index.html — fetch('/.auth/me') inside the boot x-init, used only to decide gate vs content.
  2. In nav/main_nav.html — fetch('/.auth/me') inside the nav component's x-data init(), used to display user identity.

This means every navigation (including deep-link refreshes) triggers two sequential HTTP round-trips to the same endpoint, for data that is already available in the browser's SWA auth layer.

Solution

Lift checkAuth() into the shared boot module (Candidate 1) and make the nav component read from a shared cache (e.g., an Alpine store or a DOM data attribute set during boot).

Specifically: after the boot sequence resolves auth, store window.__auth = data.clientPrincipal or set it into an Alpine.store('auth', ...). The nav template reads from Alpine.store('auth').user instead of calling /.auth/me.

Benefits

  • Leverage — one shared seam for auth state instead of two ad-hoc fetch calls with no coordination.
  • Locality — if the auth data model changes (e.g., claims structure), there's one place to update.
  • Performance — saves one HTTP round-trip per navigation.

3. Missing data/domain layer behind the API handlers

api/src/blueprints/api_routes.py (and beyond)

Worth exploring

Problem

The API handlers in api_routes.py hardcode mock data and inline business logic (validation) directly in the HTTP handler. The local.settings.json contains DATA_SOURCE=mock, suggesting the template intended an abstraction, but it was never built.

  • Validation lives inside the greet() handler. If validation rules change, the HTTP handler changes — even though validation is a domain concern, not a transport concern.
  • Data access is inline: items = [dict(...)]. Swapping to a database means editing the handler for every endpoint.
  • No seam to unit test business logic without an HTTP context.

Solution

Introduce a thin domain layer under api/src/domain/:

  • domain/greeting.py — validate_name(name) → dict[str, str] and create_greeting(name) → dict (pure functions, testable without Azure Functions SDK).
  • domain/repository.py — an abstract ItemRepository protocol with methods like list_items() → list[Item].
  • domain/models.py — dataclasses for Item, Greeting, etc.

Handlers become thin: read from request, call domain function, wrap in AlpineAjaxResponse. The DATA_SOURCE config selects between a MockItemRepository and a future CosmosItemRepository.

Benefits

  • Leverage — a validate_name() function with a small interface (string → errors dict) provides validation for all current and future name inputs.
  • Locality — business rules live in one place, not scattered across handlers.
  • Testability — domain functions are pure Python, testable with pytest and no Azure emulator. Repository protocol can be mocked for handler tests.

4. AlpineAjaxResponse — hidden dependency on global jinja_env

api/src/core/responses.py ← api/src/core/jinja_env.py

Worth exploring

Problem

AlpineAjaxResponse.__init__() directly references the jinja_env module-level singleton from jinja_env.py: 

from .jinja_env import jinja_env

class AlpineAjaxResponse(func.HttpResponse):
    def __init__(self, template_name, ...):
        ...
        html_content = jinja_env.get_template(template_name).render(**context)

This means:

  • Every test that constructs an AlpineAjaxResponse needs a real jinja2.Environment with real template files on disk.
  • There's no seam to inject a different renderer (e.g., for testing, or for a future template engine).
  • The AlpineAjaxResponse is doing two things: it's both an HTTP response constructor and a template renderer.

Solution

Separate the rendering concern from the response construction:

  • Keep AlpineAjaxResponse as a response builder, but accept a renderer callable with signature (template_name, context) → str.
  • Default it to the global jinja_env render, but allow injection for tests: AlpineAjaxResponse(..., renderer=lambda t, c: "<div>test</div>").
  • Or: extract a FragmentRenderer protocol/class that owns the Jinja2 environment, and pass it to the constructor.

Benefits

  • Testability — tests don't need real template files.
  • Locality — if the rendering engine changes (e.g., add template caching or switch to JinjaX), only the FragmentRenderer changes, not the response class.
  • Leverage — small interface: render(template, context) → str.

5. No error boundaries for fragment loading

app/index.html, app/_views/page2.html

Speculative

Problem

Every x-init="$ajax(...)" call lacks error handling. Alpine AJAX does not automatically surface network or server errors. When a fragment request fails:

  • The user sees a permanent "Loading…" or blank area.
  • No retry, no fallback, no user-facing error message.
  • Errors are silently swallowed unless a @ajax:error event listener is attached.

Solution

Add a lightweight wrapper or a global event listener:

  • Option A — Attach a @ajax:error listener on #app-shell (or document.body) that replaces the fragment's placeholder with a DaisyUI alert alert-error containing "Failed to load this section."
  • Option B — Use $ajax(...).catch(...) in x-init for critical fragments (boot sequence, nav).

Benefits

  • Locality — one handler catches all fragment failures. No per-component error handling needed.
  • Leverage — a small global listener provides consistent error UX across all current and future fragments.

★

Top Recommendation

Tackle Candidates 1 + 2 together: Extract the boot sequence into a shared module with cached auth.

These two candidates are interdependent — solving the boot monolith naturally creates a home for the shared auth cache, which eliminates the duplicate /.auth/me call in the nav. Together they deliver the highest leverage per change:

  • One module (app/_shared/boot.js) replaces two scattered fetch-and-decide blocks.
  • Auth is cached — the nav reads from the store instead of making a second HTTP call.
  • Error handling can be added in one place (boot + global listener).
  • No interface changes to the backend — purely a front-end refactor.

Why not Candidate 3 (domain layer)? It's the right long-term investment, but for a template that's still proving its shape, premature domain extraction adds ceremony. The boot/auth refactor pays immediate dividends in every session.
